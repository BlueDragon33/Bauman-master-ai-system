# 3. MODULE STATE MACHINE

Each Python module is exactly one of:

`NOT_STARTED`

`BASELINING`

`ACTIVE`

`VALIDATING`

`PASS`

`FAIL`

`BLOCKED`

`NEEDS_REVALIDATION`.

No “mostly done”.

---

# 4. ENTRY RULE

A module starts only when:

- required upstream owner is sufficiently stable;
- current main SHA is known;
- impacted scope is known;
- no unresolved blocker invalidates the work;
- exact constitution clauses to load are identified.

Do not rerun unrelated modules by habit.

---

# 5. EXIT RULE

A module may PASS only when:

- owned deliverables are complete;
- runtime behavior is verified where relevant;
- Python-specific invariants are tested;
- learner/browser journeys pass where relevant;
- evidence exists;
- no unresolved blocker/critical remains in scope;
- migration/rollback exists when state/schema changed;
- downstream input contract is explicit.

A green linter alone is insufficient.

A correct stdout alone is insufficient.

An AI-generated explanation alone is insufficient.

---

# 6. CHANGE CLASSES

`A PRESENTATION`

Visual/layout only.

`B DOMAIN BEHAVIOR`

Python learning/runtime behavior changes without canonical schema/state identity change.

`C DATA/SCHEMA`

Canonical programming entity/content shape/identity changes.

`D LEARNER STATE`

Attempt/mastery/review/project-history changes.

`E ARCHITECTURE/PROTOCOL`

Owner/capability/runtime/provider contract changes.

`F RELEASE/INFRA`

Execution sandbox/dependency/build/deploy/security changes.

---

# 7. INVALIDATION RULE

Change impact determines revalidation.

Examples:

- CSS-only code-editor fix → PYTHON05 + relevant PYTHON06 UX tests;
- assessment equivalence change → PYTHON03 + PYTHON06;
- interpreter-version change → PYTHON02–PYTHON06;
- sandbox protocol change → PYTHON04 + PYTHON05 + PYTHON06;
- curriculum prerequisite change → PYTHON02 + downstream affected evidence.

Do not invalidate PYTHON01 unless current-reality assumptions themselves changed materially.

---

# 8. RUNTIME TRUTH HIERARCHY

Authority order for Python behavior:

1. supported Python language/runtime specification and authoritative official documentation appropriate to the supported version;
2. deterministic execution in the supported runtime under controlled environment;
3. validated project-specific canonical examples/tests;
4. curated explanations;
5. AI/tool suggestions.

A formatter/linter/style rule is not language semantics.

A third-party package's behavior is version-specific and must use that package's authoritative contract where relevant.

---

# 9. VERSION TRUTH

PYTHON01 must prove the runtime/toolchain actually used.

Do not hard-code a Python minor version in the prompt unless repository requirements prove it.

Any behavior that varies by Python/package version must carry version context in content/tests.

---

# 10. SUBJECT BOUNDARY ROUTING

If a task is primarily about:

- algorithmic complexity/theory → route to Algorithms subject;
- SQL/database theory → Database subject;
- OS/process/network theory → appropriate systems subject;
- AI/ML theory → AI/ML subject;
- mathematical derivation → Math subject.

Python may implement these, but must not become canonical owner of adjacent theory.

---

# 11. CODE-AS-EVIDENCE RULE

Learner evidence may include:

- source code;
- execution behavior;
- test results;
- trace/state reasoning;
- debugging diagnosis;
- explanation;
- project artifact.

Clicks/opening a notebook are not mastery evidence.

---

# 12. FINAL-OUTPUT RULE

Correct final output does not automatically prove correct reasoning or robust implementation.

Assessment may need to distinguish:

- correct algorithm/logic;
- accidental hard-coded output;
- partial-case solution;
- unsafe implementation;
- non-reproducible notebook state;
- code that passes public but fails valid hidden cases.

---

# 13. AI AUTHORITY BOUNDARY

AI may:

- explain;
- ask diagnostic questions;
- provide hints;
- review code;
- suggest tests;
- help debug;
- generate temporary practice.

AI may not silently:

- mark official mastery;
- change official score;
- become runtime truth source;
- bypass sandbox;
- alter canonical content without authoring workflow;
- expose hidden official tests/answers.

---

# 14. TOOL AUTHORITY BOUNDARY

Tools such as:

- linter;
- formatter;
- type checker;
- test runner;
- debugger;
- profiler;

provide signals.

Their output must be interpreted according to their actual contracts.

No tool is automatically a universal correctness oracle.

---

# 15. EVIDENCE HIERARCHY

Prefer:

1. runtime/test evidence;
2. schema/static evidence;
3. content/provenance evidence;
4. screenshots/logs;
5. prose claims.

“Looks correct” is weak evidence.

---
