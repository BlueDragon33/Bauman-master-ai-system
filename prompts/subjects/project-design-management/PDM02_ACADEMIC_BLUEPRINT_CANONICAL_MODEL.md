# PROJECT OBJECTIVE

Defines desired project/design outcome.
Not the same as a technical requirement.

# SCOPE

Explicit boundaries and assumptions.

# DELIVERABLE

A reviewable output/result.
Not synonymous with “task”.

# DELIVERABLE CRITERION

Definition of acceptable/complete evidence.

# DESIGN ACTIVITY

Work performed to produce/evaluate a deliverable.

# WORK PACKAGE

If course supports:
bounded unit of planned work tied to deliverable/owner/estimate.

# DEPENDENCY

Typed prerequisite/relationship between activities/deliverables.

# MILESTONE

Zero-duration checkpoint/event with defined criteria/evidence, if actual methodology uses it.

# REVIEW

Design review with entry/exit criteria and open actions.

# RESPONSIBILITY

Who is accountable/responsible/consulted/informed or actual supported responsibility model.

# RESOURCE NEED

Capability/person/tool/environment requirement if scope supports.

# ESTIMATE

Effort/duration/cost estimate with method/assumption/range.
Do not present estimate as certainty.

# PLAN BASELINE

Approved project/design plan snapshot.
Changes create governed revision.

# PROGRESS EVIDENCE

Evidence of actual deliverable/work state.

# STATUS SNAPSHOT

Point-in-time view based on source artifacts.

# PROJECT RISK

Project/design-management risk.
Technical system risk remains linked to LSE owner when applicable.

# CHANGE REQUEST

Proposed change to scope/plan/deliverable or linked technical artifact.

# IMPACT ANALYSIS

May include:
scope,
deliverables,
dependencies,
schedule,
resources,
cost,
risk,
quality,
technical lifecycle artifacts
according actual course.

# DECISION RECORD

Decision + alternatives + rationale + evidence + consequences.

# ISSUE

Observed problem requiring action, distinct from uncertain risk.

# ACCEPTANCE RECORD

Acceptance of deliverable according criterion/authority.

# HANDOFF

Transfer of accepted deliverables/context/evidence to downstream lifecycle owner.

# LESSON LEARNED

Evidence-based reflection for future planning.

# LSE BOUNDARY

PDM references LSE requirements/baselines/reviews but does not redefine them.

# OOPSE BOUNDARY

PDM tracks design deliverables; OOPSE owns technical design semantics.
