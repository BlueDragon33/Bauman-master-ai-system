---

# 4. ENTRY RULE

A module starts when:

- required upstream owner is stable enough for the task;
- current main SHA is known;
- impacted scope is known;
- no unresolved blocker invalidates the task;
- constitution clauses to load are identified.

Do not require unrelated modules to rerun.

---

# 5. EXIT RULE

A module may PASS only when:

- its owned deliverables are complete;
- runtime behavior is verified where applicable;
- relevant automated tests pass;
- relevant browser/user journey passes;
- evidence exists;
- no unresolved blocker/critical remains in scope;
- downstream contract is explicit.

CI alone is insufficient.

# 8. FOUR-CONSTITUTION REVIEW

For every major change ask:

## C1 Architecture

Can this be content, manifest, adapter, capability or extension instead of Core modification?

## C2 UI/UX

Can it use existing Bauman shell, layout, components, tokens and interaction patterns?

## C3 QA

What user journey, edge case, regression, offline/mobile/accessibility/security risk must be tested?

## C4 Real Learning

Which competency does it teach?

Which evidence can prove performance?

Does it accidentally equate exposure/progress with mastery?

---

# 10. REVALIDATION RULE

A PASS module becomes `NEEDS_REVALIDATION` only when a later change touches:

- its canonical owner;
- its contract;
- its data/state;
- an upstream truth source it consumes;
- a runtime dependency that can alter its behavior.

A CSS-only change does not automatically rerun curriculum.

A vocab-content correction does not automatically rerun production release architecture.

---

# 11. HANDOFF RULE

Each RU module outputs one compact handoff containing:

- current/base SHA;
- changed owners;
- new/changed contracts;
- evidence;
- known risks;
- downstream assumptions;
- exact modules needing revalidation.

The next module consumes the handoff instead of rediscovering everything.
