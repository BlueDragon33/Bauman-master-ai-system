# 3. MODULE STATE MACHINE

Each Math module is exactly one of:

`NOT_STARTED`

`BASELINING`

`ACTIVE`

`VALIDATING`

`PASS`

`FAIL`

`BLOCKED`

`NEEDS_REVALIDATION`.

Do not use vague status:

- mostly done;
- likely fine;
- almost pass.

---

# 4. ENTRY RULE

A module starts only when:

- required upstream owner is sufficiently stable;
- current main SHA is known;
- impacted scope is known;
- no unresolved blocker invalidates the work;
- exact constitution clauses to load are identified.

Do not require unrelated modules to rerun.

---

# 5. EXIT RULE

A module may PASS only when:

- owned deliverables are complete;
- runtime behavior is verified where relevant;
- mathematical invariants are tested;
- relevant browser/user journeys pass;
- evidence exists;
- no unresolved blocker/critical remains in scope;
- migration/rollback exists when state/schema changed;
- downstream input contract is explicit.

CI green alone is insufficient.

A beautiful graph alone is insufficient.

A CAS result alone is insufficient.

---

# 8. FOUR-CONSTITUTION REVIEW

For every major change ask:

## C1 Architecture

Can this be expressed through:

- content;
- manifest;
- registry;
- adapter;
- capability;
- extension;
- reusable block;

instead of platform Core modification?

## C2 UI/UX

Does it use:

- shared App Shell;
- shared components;
- responsive/accessibility contracts;
- consistent loading/error states?

## C3 QA

Can failure be reproduced and automatically/manual regression-tested?

## C4 Learning

Which competency and evidence does this support?

If the answer to C4 is “it looks educational”, the feature is not justified.

# 10. TOKEN ROUTER

Default execution context:

1. this master file;
2. active MATH module;
3. exact constitution sections from `MATH_CONSTITUTION_ROUTER.json`;
4. current status/evidence;
5. diff from last validated SHA;
6. impacted source files/tests.

Do not load the full prompt estate by default.

---

# 11. REVALIDATION RULE

A PASS module becomes `NEEDS_REVALIDATION` only when a later change touches:

- its canonical owner;
- its contract;
- its schema/state;
- a dependency whose output semantics changed.

Examples:

- typography-only change does not invalidate mathematical equivalence;
- changing expression parser may invalidate MATH03, MATH04, MATH05 and MATH06;
- changing mastery semantics may invalidate MATH03 and downstream acceptance.

---

# 12. HANDOFF RULE

Every module emits:

- status;
- base/head SHA;
- owner changes;
- evidence index;
- known limitations;
- downstream input contract;
- exact revalidation triggers.

Downstream module consumes this handoff instead of rediscovering everything.

---

# 13. AUTONOMOUS WORK RULE

Within authorized scope, Work/Codex should:

`inspect → edit → test → repair → rerun → document → commit/PR`

without asking about ordinary technical decisions.

Ask only for:

- credentials/external authorization;
- destructive action without safe rollback;
- irreversible product/academic choice;
- ambiguous curriculum requirement that materially changes outcomes.

---

# 14. NO CONTENT EXPLOSION

Do not generate hundreds/thousands of new Math exercises merely because schemas exist.

Order:

`AUDIT → CANONICALIZE → BUILD VALIDATOR/ENGINE → PILOT → VALIDATE → SCALE`.

Quality and reasoning coverage outrank raw record count.

---

# 15. PRODUCTION RULE

MATH01–MATH06 do not declare production success.

MATH06 creates an exact RC-ready Math profile.

Shared production release procedure performs:

`preflight → backup/migrate if needed → deploy/promote exact RC → activate exact content → smoke → verify → observe → rollback/close`.

No “latest build” release.

---

# 16. FINAL MATH00 INVARIANT

At any moment the system must be able to answer:

- Who owns this mathematical fact?
- What assumptions/domain make it true?
- Who owns this learner evidence?
- Is this output exact, approximate, visual, computational or AI-generated?
- Which constitution governs the change?
- Which tests prove it?
- Which downstream modules require revalidation?

If these answers are ambiguous, expand evidence before expanding features.
