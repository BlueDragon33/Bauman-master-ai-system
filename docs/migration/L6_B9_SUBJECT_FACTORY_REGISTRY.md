# L6-B9 · Subject Factory registry and secure source resolver

Status in this record is **implementation pending remote CI** until the B9
commit status is successful. This document does not by itself declare PASS.

## 1. Decision

L6-B9 registers the eight current Main subjects as read-only Subject Factory
profiles. It binds each profile to an existing engine, one deterministic
primary lesson-type policy, specialist widgets, registered local data sources
and the L5 offline-pack limits. It also adds a dependency-free browser UMD
resolver that validates and resolves those declarations without fetching,
rendering, migrating or persisting anything.

The artifacts are:

| Artifact | Role |
| --- | --- |
| `assets/data/lesson/subject-factory-registry-v1.json` | Versioned subject, engine, widget, source and offline registry |
| `assets/js/platform/universal-lesson/subject-factory-registry-v1.js` | Fail-closed validator and deterministic resolver |
| `scripts/academic/l6-b9-subject-factory-regression.cjs` | Source-to-registry, classification, security and mutation gate |
| `docs/migration/L6_B9_SUBJECT_FACTORY_REGRESSION.generated.json` | Machine-readable evidence generated by the gate |

B9 does not activate the Universal Lesson Renderer. Runtime projection and
legacy bridges belong to B10; reference-subject browser/offline validation
belongs to B11.

## 3. Deterministic lesson-type classification

An explicit type supplied by reviewed context is accepted only when that type
is allowed by the subject profile. Otherwise the resolver evaluates registered
rules. Rules are keyed by stable lesson/module IDs, never array positions. Two
rules producing different primary types cause `AMBIGUOUS_LESSON_TYPE`.

Programming defaults to `programming`. `PR06`, `PR15`, `PR20` and `PR21` map to
`database`; `PR17`, `PR18`, `PR19`, `PR22`, `PR24`, `PR30`, `PR32`, `PR38`,
`PR39`, `PR40`, `PR41`, `PR43`, `PR44`, `PR46`, `PR47` and `PR48` map to
`software-design`.

Foundation is intentionally fail-closed because its current modules mix
language, mathematics, computing, entrepreneurship and legal/civic content.
Only the following mappings are safe in B9:

- `f_s01` and `f_s05` → `language`;
- `f_s02` and `f_s04` → `mathematics`;
- `f_s03` → `programming`;
- `f_m201` and `f_m202` → `UNCLASSIFIED_LESSON`, pending content/type review.

Foundation therefore has no default primary type. B9 does not force the last
six lessons through an unrelated type merely to claim full coverage.

## 4. Source inventory and load classes

A source belongs to exactly one of four classes: `startup`, `required-lazy`,
`optional-lazy` or `runtime-supplemental`. The resolver accepts only safe
repository-relative paths under the registered subject data root. Protocols,
absolute paths, traversal, query strings, fragments, unsafe IDs, duplicate
class membership and unknown sources fail closed.

The inventory is reconciled against the current subject adapters, JSON
manifests and runtime constants:

- Russian registers all 17 adapter sources. `vocab`, `tests` and `speaking`
  remain required academic sources but are `required-lazy`; they are not placed
  in the legacy optional/persistence-exclusion list. The three native optional
  sources remain `optional-lazy`.
- Mathematics registers the 58 adapter sources plus the audited
  `lessons-deferred` startup compatibility file. Full `lessons.json` is
  `required-lazy`; `theory_lecture_content` and the registered artifact-reader
  path precede explicit legacy lessons.
- Programming registers the 15 startup and two optional adapter sources.
- Each of the five light subject manifests lists six JSON files while its
  current runtime loads a seventh, `simulations.json`. B9 records simulations
  as `runtime-supplemental` and does not rewrite a working manifest or runtime.

Unregistered files are never guessed. They remain owned by the specialist
engine until a later audited registry change.

## 5. Widget registry and fallbacks

The registry distinguishes `existing`, `existing-lazy`, `declared` and planned
widget states. Existing specialist widgets may be selected only for a
compatible lesson type. Declared and planned widgets resolve to their committed
deterministic fallback; they are never reported as implemented.

Every widget declares a fallback and explicit Master-ready evidence authority.
Planned widgets must use `none-until-implemented`; a planned code runner, SQL
playground, signal plot or systems workspace cannot manufacture Master-ready
evidence before its owning round implements and validates it.

## 6. Offline boundary

Every registered offline policy preserves the L5 limits:

- base pack maximum per resource: 5 MiB;
- explicit session maximum per resource: 64 MiB;
- discovery: runtime network probe;
- silent whole-repository precache: forbidden;
- generative AI requirement: false;
- deterministic local fallback: required.

Large current Russian and Mathematics JSON sources are therefore deferred from
the base startup set. B9 only describes source classes and existing pack
policy; it does not change the service worker or turn production cache on.

## 7. Resolver boundary

The resolver exports pure operations for registry validation, subject lookup,
lesson-type classification, data-source lookup, widget lookup and descriptor
construction. It has no DOM, network, Cache Storage, IndexedDB or localStorage
dependency. Returned records are cloned so callers cannot mutate the registry
through a descriptor.

Validation also locks the four audit decisions that are easy to regress:

1. light-runtime simulations remain supplemental;
2. Foundation remains a scoped fail-closed pilot;
3. Mathematics keeps authoritative theory precedence and deferred legacy data;
4. Russian heavy required sources remain persistence-safe required-lazy data.

The registry digest is SHA-256 over stable JSON using the B8 validator. This is
integrity evidence, not an authorization to write or migrate data.

## 8. Rollback

B9 changes no learner content, state, subject runtime, storage key or offline
cache. Repository rollback removes the B9 registry, resolver, decision record,
generated report and workflow step, then restores progress markers to the B8
checkpoint. Existing Russian, Mathematics, Programming and light-subject
engines continue unchanged throughout.
