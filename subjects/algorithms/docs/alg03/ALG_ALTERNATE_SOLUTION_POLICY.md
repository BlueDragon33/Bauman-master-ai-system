# ALG03 ALTERNATE SOLUTION POLICY

**Grade the algorithmic contract, not the shape of one reference solution.** Source-string equality is forbidden as the primary grader.

A task declares one of: `SPECIFIC_ALGORITHM_REQUIRED`, `ALGORITHM_FAMILY_REQUIRED`, or `ANY_CONTRACT_COMPLIANT_ALGORITHM`. A candidate is accepted when all declared hard requirements hold: functional postcondition, preconditions, representation constraints, complexity/memory targets, stability/order/tie rules, mutation policy and required reasoning evidence.

Different code structures/helper decomposition or implementation languages are valid when course policy permits and the same contract is satisfied.

Multiple valid outputs use properties/constraints: any-match binary search, graph traversal with unspecified neighbor order, tied BFS parents and unordered set-like outputs must not be rejected because they differ from one reference sequence.

Functional correctness and complexity compliance are recorded separately. A linear search can be functionally correct but complexity-noncompliant on a task requiring logarithmic search.

Language syntax/runtime mistakes route to the language owner when appropriate and are not automatically algorithm misconceptions.

Deferred-JIT topics require a canonical topic contract before official assessment.
